## 2. What Differs Between Failed and (Partially) Successful Runs

### 2.1 GPT-5.4 Temperature Crash (R2: `430f1dc9`)

Run R2 used `config/config.exp-gpt5.yaml` which set `temperature: 0.5` for the boss agent. GPT-5 models only support `temperature=1`. LiteLLM rejected the parameter immediately:

```
LLMError("Unexpected LLM error for model 'openai/gpt-5.4':
  litellm.UnsupportedParamsError: gpt-5 models (including gpt-5-codex)
  don't support temperature=0.5. Only temperature=1 is supported.
  For gpt-5.1, temperature is supported when reasoning_effort='none'.")
```

**Fix**: `config.exp-gpt5.yaml` must set `temperature: 1.0` for all agents. Run R3 (`c8be9957`) corrected this and successfully decomposed the task.

### 2.2 Assessment Heuristics Killed Run v2 Entirely

Run v2 (`03a21736`, March 29) died instantly because the concreteness/completeness scoring in the assessment stage scored all 3 subtasks below 0.35:

| Subtask | Score | Reason |
|---------|-------|--------|
| "Analyze the sanitizer stack trace to identify the root cause" | 0.00 | Too abstract |
| "Build the project with address sanitizer enabled" | 0.35 | Below threshold |
| "Ensure the build script is standalone and optimized" | 0.35 | Below threshold |

The LLM also produced string dependency references (e.g. `['/src/build.sh']`) instead of integer indices, causing `depends_on` parsing warnings.

**Fix applied**: Commit `079ed62` removed the concreteness/completeness quality validators entirely, trusting the LLM's decomposition judgment. This allowed today's runs (R1, R3, R4) to successfully decompose and spawn children.

### 2.3 Workers Go Off-Task (v1, v3, v4)

The OpenHands workers, given a focused subtask like "build njs with ASan", frequently deviated:

- **v1**: Final worker was inspecting `/proc/meminfo` (grep for Slab, SReclaimable) instead of working on the CVE
- **v4**: Last worker was reading the full git commit history of the njs project instead of crafting a PoC
- **v3**: Stuck detection triggered after action/observation loop at 17:43:45

This manifests as the `User Paused` / `Conversation Paused` events when OpenHands workers hit the `max_iterations` cap (20 iterations in v1-v4, now configurable to 50 in experiment configs).

### 2.4 Verification Correctly Rejects, But Workers Don't Improve

The 4-stage verification pipeline (structural -> deterministic -> execution -> LLM judge) is working correctly. It rejected 4 results in v1, 5 in v3, and 10 in v4. However, the retry mechanism (re-executing the worker after rejection) doesn't feed the judge's rejection reasoning back to the worker. The worker restarts from scratch with the same prompt and makes similar mistakes.

### 2.5 Code Changes Between Sessions

Commit `079ed62` (Mar 29, 21:20, **after** all v1-v4 failures):

| Change | Impact |
|--------|--------|
| Removed quality validators (concreteness/completeness heuristics) | Unblocks v2-style assessment failures |
| Loosened topology: `max_children=5`, `max_total=25` | Unblocks v3/v4 `total_agents` limit violations |
| Wired auto-healing retry with gpt-4-turbo escalation | Enables model escalation on LLM errors |
| Added `assess.j2` domain reference material | Gives assessor CVE-specific context |
| Added experiment configs (`config.exp-gpt4o.yaml`, `config.exp-gpt5.yaml`) | Per-model experiment control |
| Added command filter + worker adapter base class | Blocks dangerous commands in workers |
| Increased worker `max_iterations` to 50 (experiment configs) | Gives workers more room to work |

## 3. Topological Variance Across Runs

The same task ("Reproduce and patch CVE-2022-32414") produces wildly different agent trees depending on the model and temperature:

### GPT-4o (temp=0.5) — Runs R1 and R4

```
BOSS (gpt-4o)
├── [Builder] Build njs with ASan — assessed SIMPLE → WORKER
├── [Exploiter] Create PoC for SEGV — assessed SIMPLE → WORKER
└── [Fixer] Develop minimal patch — assessed COMPLEX → MANAGER
    ├── Reproduce the SEGV using sanitizers — WORKER
    ├── Develop a minimal patch — WORKER
    └── Verify patch fixes the issue — WORKER

Total: 7-8 agents, depth 3, sequential depends_on (R1) or all independent (R4)
```

**Assessment reasoning**: GPT-4o consistently sees Builder and Exploiter as simple (single-concern tasks) but Fixer as complex (reproduce + patch + verify = 3 distinct steps).

### GPT-5.4 (temp=1.0) — Run R3

```
BOSS (gpt-5.4)
├── [Builder] Check out f65981b0..., produce sanitizer build — assessed SIMPLE → WORKER
├── [Exploiter] Reproduce CVE via njs_vmcode_interpreter crash path — assessed SIMPLE → WORKER
└── [Fixer] Analyze root cause, implement patch, generate model_patch.diff — assessed SIMPLE → WORKER

Total: 4 agents, depth 2, all independent
```

**Assessment reasoning**: GPT-5.4 assessed ALL subtasks as simple with notably more specific reasoning ("single focused bugfix in one interpreter function"). Its decomposition was also far more detailed:

- Builder had 5 `target_paths`, 5 `search_hints`, and explicit `success_criteria`: "Repository is at the specified base commit; `./src/build.sh` builds njs successfully with address sanitizer enabled; `./testcase/base_commit_hash` exists..."
- Exploiter had 6 `search_hints` including "CVE-2022-32414", "njs_vmcode_interpreter segv", "invalid bytecode"
- Temperature was varied per-subtask: Builder 0.3, Exploiter 0.4, Fixer 0.3

### March 29 Runs (v1, v3, v4)

```
BOSS
├── [Builder] Manager → 3-4 Workers (depth 2-3)
├── [Exploiter] Manager → 3-4 Workers (depth 2-3)
└── [Fixer] Manager → 3-4 Workers (depth 2-3)

Total: 13 agents, depth 3-4, hit max_total_agents=25 cap on further decomposition
```

**Problem**: The middle-layer managers (depth 1) decomposed Builder into sub-tasks like "Analyze root cause", "Review fixes", "Create patch", "Validate patch" — each of which became a separate worker. This over-decomposition:
- Exhausted the agent budget (13/25)
- Created coordination overhead without clear benefit
- Workers at depth 3-4 had very narrow scope but still went off-task

### Dependency Modeling Inconsistency

| Run | Model | Dependency Strategy |
|-----|-------|---------------------|
| R1 (a9ae) | gpt-4o | Proper chain: `Builder[0] → Exploiter[1] → Fixer[2]` |
| R3 (c8be) | gpt-5.4 | All independent: `depends_on: []` for all |
| R4 (eee1) | gpt-4o | All independent: `depends_on: []` for all |

## 5. Identified Problems

### P1: GPT-5 Temperature Incompatibility
- **Severity**: Blocking
- **Impact**: Run R2 crashed immediately
- **Root cause**: `config.exp-gpt5.yaml` sets `temperature: 0.5` for boss; GPT-5 only supports `temperature: 1`
- **Fix**: Set `temperature: 1.0` in all GPT-5 configs, or use `litellm.drop_params = True`

### P2: Topological Variance Is Uncontrolled
- **Severity**: High
- **Impact**: Same task produces 4-agent flat trees (R3) or 13-agent deep trees (v1/v3/v4)
- **Evidence**: GPT-4o Fixer is consistently assessed as "complex" and decomposes; GPT-5.4 assesses everything as "simple"
- **Risk**: Deep trees exhaust agent budgets and increase coordination failure probability
- **Observation**: The flattest decomposition (R3, GPT-5.4) produced the most detailed and actionable subtask descriptions

### P3: Workers Go Off-Task Under Multi-Agent Orchestration
- **Severity**: High
- **Impact**: Workers spend iterations inspecting system memory, reading git logs, or looping instead of working on the CVE
- **Evidence**: v1 (final worker on /proc/meminfo), v4 (worker reading full git history), v3/v4 (stuck pattern detection)
- **Contrast**: Standalone SEC-bench verifier workers succeed 78% because they receive a complete, focused prompt with all CVE context in one shot

### P4: Verification Rejects Without Teaching
- **Severity**: Medium
- **Impact**: 10 verification rejections in v4 alone, but retried workers make the same mistakes
- **Root cause**: Rejection reasoning from the LLM judge is not fed back into the worker's retry prompt
- **Opportunity**: Feed judge feedback as additional context to the retry prompt

### P5: Dependency Modeling Is Non-Deterministic
- **Severity**: Medium
- **Impact**: Only 1/8 runs produced correct sequential `depends_on` chains
- **Root cause**: LLM sometimes produces string references instead of integer indices; assessment prompt doesn't enforce dependency reasoning
- **Evidence**: v2 logged `dropped non-integer depends_on values` warnings

### P6: Database Was Reset Between Sessions
- **Severity**: Low (operational)
- **Impact**: Yesterday's run data exists only in log files, not queryable via DB
- **Recommendation**: Preserve event store across experiment sessions, or archive to JSONL before reset

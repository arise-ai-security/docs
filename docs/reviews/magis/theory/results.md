# Results & Analysis

## Overall Performance (RQ2)

MAGIS is evaluated on a 25% subset of SWE-bench (the same subset used in the original GPT-4 experiments), using GPT-4 as the base LLM.

| Method | % Applied | % Resolved |
|---|---|---|
| GPT-3.5 | 11.67 | 0.84 |
| GPT-4 | 13.24 | 1.74 |
| Claude-2 | 49.36 | 4.88 |
| SWE-Llama 7b | 51.56 | 2.12 |
| SWE-Llama 13b | 49.13 | 4.36 |
| **MAGIS** | **97.39** | **13.94** |

MAGIS achieves an **eight-fold increase** in resolved ratio over direct GPT-4 and nearly **three-fold** over the previous best (Claude-2). The applied ratio of 97.39% indicates that MAGIS almost always produces valid patches, compared to only 13.24% for direct GPT-4.

## Ablation Study

| Variant | % Applied | % Resolved |
|---|---|---|
| MAGIS (full) | 97.39 | 13.94 |
| MAGIS (w/o QA) | 92.71 | 10.63 |
| MAGIS (w/o hints) | 94.25 | 10.28 |
| MAGIS (w/o hints, w/o QA) | 91.99 | 8.71 |

- **Without QA Engineer**: Resolved ratio drops by 3.31 percentage points, confirming the value of iterative code review
- **Without hints** (PR comments from humans): Resolved ratio drops by 3.66 percentage points, showing that human participation can further improve resolution
- **Without both**: Still achieves 8.71% — a five-fold improvement over base GPT-4, demonstrating that the multi-agent architecture itself is the primary contributor

## Planning Effectiveness (RQ3)

### Repository Custodian
The Custodian's BM25 + LLM filtering consistently outperforms plain BM25 across varying numbers of selected files. It achieves higher recall scores with fewer files — identifying the maximum number of relevant files with minimal selection.

### Manager
Task descriptions generated by the Manager are evaluated for alignment with reference code changes using GPT-4 as a judge. Most task descriptions score 3 or above (on a 1–5 scale), indicating correct planning direction. Higher correlation scores correspond to higher resolution probability.

## Coding Effectiveness (RQ4)

### Line Locating
MAGIS Developers achieve significantly higher line locating coverage ratios compared to baselines. The distribution is concentrated near 1.0, while baselines concentrate near 0.0. Higher coverage ratios correspond to higher resolved ratios, confirming that accurate line locating is critical for issue resolution.

### Complexity Handling

| Method | # Files | # Functions | # Hunks | # Added LoC | # Deleted LoC | # Changed LoC |
|---|---|---|---|---|---|---|
| GPT-4 | −25.15\* | −25.15\* | −0.06 | −0.10 | −0.04 | −0.21 |
| MAGIS | −1.55\* | −1.55\* | −0.12\* | −0.04\* | −0.06\* | −0.57\* |

\* P-value < 0.05

MAGIS shows much weaker negative correlations for the number of files and functions compared to GPT-4 (−1.55 vs. −25.15), indicating that the framework effectively mitigates the complexity challenge through task decomposition.

### QA Engineer Contribution
The QA Engineer improves resolved ratio by 1.57% (with hints) and 3.31% (without hints). The iterative review-revise loop helps catch and correct errors that single-pass generation misses.

## Comparison with Devin (App. E)

On the shared 140-instance overlap, MAGIS resolves **21 issues (15%)** vs Devin's **18 (12.86%)**. MAGIS relies solely on shell access with no internet; Devin uses browser and external tools. MAGIS also resolves each instance in an average of **~5 minutes**, vs Devin where 72% of resolved instances take >10 minutes.

## Limitations

The paper acknowledges several limitations:
- Evaluation is on a 25% subset of SWE-bench, not the full dataset
- Only GPT-4 is used as the base LLM (Claude-2 API was unavailable)
- The 13.94% resolved ratio, while a significant improvement, still means 86% of issues remain unresolved
- The framework assumes issues can be decomposed into file-level tasks, which may not suit all types of changes

# Design Choice 3: Recursive Planning and Working With Fair Budget Allowance + Tree Growth Control + Better Inherited Prompting

## Budgeted Tree-Structured Agentic System 
This design choice builds upon the [Budgeted Tree-Structured Agentic System](./budgeted_tree.md) by incorporating additional probablitic agent transitions and context inheritances mechanisms to control tree growth and enhance inherited prompting. The budget allowance is based on supervisors' own discretion to allocate budget to their worker agents based on the task complexity, importance, and necessity.

**Note**: This system has no [budget update system](/docs/projects/arise-sec-lion/system/reinforcement_learning/budget_update.md) enabled yet. This tree only restricts the excessuve growth of the tree by checking the budget allowance before spawning new agents.

### Analysis
1. **Tree Growth Control**: Russian Roullette style mechanism to probabilistically force a supervisor agent to become worker agents. As can be observed, in the [previous desgin](./budgeted_tree.md#interactive-diagram), the tree can grow without bounds, leading to overthinking and lack of real focus. This approach employs the benefits of LLM model's intrisic capability to direct implement required work without excessive delegation. This helps to maintain a more manageable tree structure and ensures that the system remains efficient and focused on task completion.

2. **Enhanced Inherited Prompting**: Worker agents receive more context from their parent supervisor agents, including supervisors' own objectives, expectations, requirements, and justifications. This method also significantly increases the accuracy and relevance of the work performed by worker agents, as they have a clearer understanding of the overall task and its goals. The context passed down is accumulative, meaning that each worker agent inherits not only the immediate supervisor's context but also the summarized context from all ancestor supervisors up to the root. This creates a rich informational environment for each agent, enabling them to make more informed decisions and produce higher-quality outputs.

3. **Fair Budget Split**:   When a supervisor (BOSS/MANAGER) decomposes a task into subtasks, it splits its budget proportionally based on each subtask's budget_weight (ranging 0.1-10.0). The LLM assigns weights considering task complexity, importance, and estimated time.

    Allocation formula: 
    $$
    \text{child budget} = \text{parent budget} × \left(\frac{\text{subtask weight}}{\text{total weights}}\right)
    $$

    For example, if a supervisor has 1000 and creates 3 subtasks with weights 1.0, 3.0, and 1.5:
    - Subtask 1 gets: $1000 × (1.0/5.5) = 182$
    - Subtask 2 gets: $1000 × (3.0/5.5) = 545$
    - Subtask 3 gets: $1000 × (1.5/5.5) = 273$

    Higher weights mean more resources for complex/critical tasks.

    Budget weights are assigned by the LLM during task decomposition based on three factors:

    1. Complexity (primary factor)
    - Simple tasks: 0.5-1.0 weight
    - Moderate tasks: 1.0-2.0 weight
    - Complex tasks: 2.0-3.0 weight

    2. Importance (critical path consideration)
    - Normal tasks: 1.0 weight
    - Important tasks: 1.5-2.0 weight
    - Critical path tasks: 2.0-4.0 weight

    3. Estimated Time (relative duration)
    - Quick tasks: 0.5-1.0 weight
    - Average tasks: 1.0 weight
    - Long tasks: proportional (2x time ≈ 2x weight)

    Examples from the prompt template:
    | Task Type               | Weight  | Rationale                          |
    |-------------------------|---------|------------------------------------|
    | Research/documentation  | 0.8-1.0 | Quick, low complexity              |
    | Standard implementation | 1.0-1.5 | Normal baseline                    |
    | Core feature with tests | 2.5-3.0 | Complex + important                |
    | Security-critical code  | 3.0-4.0 | High stakes, needs extra resources |

    Constraints:
    - Minimum weight: 0.1
    - Maximum weight: 10.0
    - Default (if unspecified): 1.0

    The weights are relative—what matters is the ratio between subtasks, not absolute values. A subtask with weight 2.0 receives twice the budget of one with weight 1.0.

4. **Low Budget Protection**: In this implementation, to avoid the supervisors' excessive delegation and usages of budget, we set a low budget transition protection rule (20% of the total entire tree budget) for supervisors to spawn new worker agents. This encourages supervisors to take on more responsibilities themselves and have to become a worker agent if the budget is low. This mechanism helps to prevent unnecessary tree growth and ensures that the system remains efficient and focused on task completion.

4. **High Performance**: Both previous two features contribute to the overall high performance of this agentic system. For the same task described above, the budgeted tree takes up to more than 200 agents but can not finish the work successfully. In contrast, this design choice completes the task with around 50 agents involved, demonstrating its efficiency and effectiveness in handling complex tasks.

5. **Unorganitzed Structure**: One drawback as shown in the Generated Files section is that the file structure generated by this agentic system is very unorganized. We should be able to mitigate the issue by introducing better prompt for every agent to follow a specific file structure convention.

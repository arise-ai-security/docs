## 1. Methodology: Security-Oriented Multi-Agent Prompt Engineering

### 1.1 The Problem: Generic Prompts Produce Shallow Security Analysis

The baseline system (pre-`4e1bb5c`) generated skeletal guidance for workers (~11 lines) and provided minimal context to thinker agents. This led to:

- **Blind decomposition**: Thinkers delegated without understanding the codebase
- **Generic tool usage**: Workers scanned entire codebases instead of targeting vulnerable files
- **Missing security tools**: Workers only used Valgrind/KLEE when cppcheck, cflow, gdb, strace, ltrace, addr2line would have been more appropriate
- **No peer validation**: Workers blindly trusted upstream findings, propagating errors

### 1.2 Methodology: 4-Layer Security-Aware Prompt Architecture

We redesigned the prompt system across 19 files (433+ insertions) into a 4-layer architecture where each layer adds security-domain intelligence:

```

### 1.4 First-Principles Patch Development (No Cheating)

A critical methodological decision: **patches must be developed from first principles**, not by searching for external fix commits or git history.

```
  BEFORE (cheating path):                 AFTER (first-principles path):
  ┌──────────────────────────┐            ┌──────────────────────────────────┐
  │ 1. git show <fix_hash>   │            │ 1. Read PoC file — understand    │
  │ 2. Apply external patch  │            │    what input triggers the bug   │
  │ 3. Done                  │            │ 2. Run PoC with GDB — get        │
  │                          │            │    precise crash stack trace     │
  │ Problem: proves nothing  │            │ 3. Trace data flow: input ->     │
  │ about understanding the  │            │    parsing -> vulnerable op      │
  │ vulnerability. A lookup, │            │ 4. Identify root cause: missing  │
  │ not analysis.            │            │    free(), null check, bounds    │
  │                          │            │ 5. Design minimal fix            │
  └──────────────────────────┘            │ 6. Implement & validate with     │
                                          │    multiple tools                │
                                          │                                  │
                                          │ Result: demonstrates genuine     │
                                          │ vulnerability understanding.     │
                                          └──────────────────────────────────┘

  Implementation:
  - Removed "candidate_fixes" from CVE display fields (prompt_strategy.py)
  - Fixer template: "Do NOT search for or apply existing external patches"
  - Boss template: "Patches must be developed from first principles"
  - Worker template: removed all git show/curl .diff references
```

## 4. Critical Fixes: Technical Deep Dive

### 4.1 Cross-Hierarchy DAG Scheduling Bug

**Bug**: Workers with `depends_on: []` within a manager could start before the manager's own parent-level dependencies were satisfied.

```
  BEFORE (buggy):
  ┌───────────────────────────────────────────────────────┐
  │ BOSS                                                   │
  │ ├── Builder (depends_on: [])                          │
  │ ├── Exploiter (depends_on: [0])  # depends on Builder │
  │ └── Fixer (depends_on: [1])      # depends on Exploit │
  │     ├── Root-Cause-Analyst (depends_on: [])           │
  │     │   ^^^ THIS STARTED AT 19:58:12                  │
  │     │       BEFORE Builder at 19:59:59!               │
  │     │                                                  │
  │     │   Because: depends_on:[] means "no sibling deps"│
  │     │   But scheduler only checked sibling deps,       │
  │     │   not whether parent (Fixer) was ready.          │
  │     └── ...                                            │
  └───────────────────────────────────────────────────────┘

  AFTER (fixed):
  _ancestors_deps_satisfied() walks up the parent chain:
  ┌───────────────────────────────────────────────────────┐
  │ Root-Cause-Analyst.ready?                              │
  │   1. Own sibling deps satisfied? YES (depends_on:[])  │
  │   2. Parent (Fixer) sibling deps satisfied?           │
  │      Fixer depends_on: [1] (Exploiter)                │
  │      Is Exploiter terminal? NO -> NOT READY           │
  │   3. Wait until Builder -> Exploiter -> Fixer chain   │
  │      completes before starting                        │
  └───────────────────────────────────────────────────────┘
```

### 4.2 Judge JSON Parse Failure

**Bug**: When the LLM judge returned markdown-wrapped JSON or extra text, `json.loads()` failed and the fallback **auto-passed every worker**.

```

## 5. Comparison: Multi-Agent vs Single-Agent

### CVE-2022-32414 (nginx/njs) — Week 2 Data

The standalone SEC-bench verifier (single-agent, no orchestration) achieved **7/9 success** on this CVE. Multi-agent (8 runs) achieved **0/8 success**.

This confirmed that the orchestration layer itself was the bottleneck, not worker capability. This motivated the entire week 3 sprint.

### CVE-2018-5247 (ImageMagick) — Week 3 Data

## 6. Peer Validation and Context Sharing

A key security methodology principle: **workers validate upstream findings rather than blindly trusting them.**

```
  ┌─────────────────────────────────────────────────────────────────────────┐
  │               Peer Validation Chain (Exploiter Phase)                   │
  │                                                                         │
  │  PoC-Researcher                                                        │
  │  ├── Searches bug report for existing PoC (download-first strategy)    │
  │  ├── If none: static analysis with cflow + cppcheck                    │
  │  └── Publishes via <context-update>:                                   │
  │      PoC path, vulnerable function, trigger conditions                 │
  │           │                                                             │
  │           ▼                                                             │
  │  Data-Flow-Analyst                                                     │
  │  ├── Validates: does the PoC file actually exist?                      │
  │  ├── Traces data flow: input -> parsing -> crash point                 │
  │  └── Publishes: exact data flow path, buffer sizes, boundary conditions│
  │           │                                                             │
  │           ▼                                                             │
  │  PoC-Tester                                                            │
  │  ├── Validates: do reported function names match source?               │
  │  ├── Validates: are binary paths correct?                              │
  │  ├── Tests with Valgrind + GDB + strace + ASan                        │
  │  └── If peer findings wrong: investigates independently                │
  │           │                                                             │
  │           ▼                                                             │
  │  Repro-Creator                                                         │
  │  ├── Validates: does PoC-Tester's exploit command work?                │
  │  └── Creates self-contained /testcase/repro.sh                         │
  │           │                                                             │
  │           ▼                                                             │
  │  Exploit-Validator (aggregation worker)                                │
  │  ├── Reviews ALL upstream findings holistically                        │
  │  ├── Runs repro.sh 3 times for deterministic reproducibility           │
  │  ├── Cross-checks: sanitizer type, crash address, source function      │
  │  └── If inconsistency found: investigates and fixes                    │
  └─────────────────────────────────────────────────────────────────────────┘

  This chain ensures that errors are caught early and don't propagate.
  In Run 6: PoC-Craftsman (paraphrased name) tried to CRAFT a PoC from
  scratch when one already existed in the bug report — the peer validation
  pattern would have caught this if the role name had been correct.
```

## 8. Blockers and Next Steps

### Resolved Blockers
- Cascade failures (partial-success aggregation)
- Over-decomposition (anti-decomposition heuristics)
- Judge parse failures (regex fallback)
- Cross-hierarchy scheduling (ancestor dependency check)
- Patch diff bloat (file-specific git diff)

### Remaining Work
1. **Scale to more CVEs**: Current validation is on 2 CVEs (ImageMagick, nginx/njs). Need to run against the full SEC-bench dataset to measure generalization
2. **Concurrency**: `max_concurrent_workers=1` forces sequential execution. Increasing to 2-3 could reduce wall time from ~43 min to ~20 min
3. **Reporter host path**: Container vs host path confusion still causes reporter failures in some runs
4. **Worker iteration budget**: Some workers exhaust 50 iterations on deep analysis — consider dynamic allocation based on task complexity
5. **Cost analysis**: Overall USD cost is low despite ~1 hour runs (o3 is cheap), but need systematic cost tracking across CVEs

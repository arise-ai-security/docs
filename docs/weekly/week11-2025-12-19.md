### 2. Results: What Happens When We Execute

**Agent Lifecycle Flow:**
```
BOSS (budget=1000)
  ├─ Spawns 3 subordinates per subtask (budget split: 333 each)
  │   ├─ Claude Sonnet → succeeds first → wins
  │   ├─ Gemini Pro → terminated (sibling won)
  │   └─ GPT-4o → terminated (sibling won)
  │
  ├─ Winner returns budget with reward (111 * 1.2 = 133.2)
  ├─ Verification heuristic check (10% random, complexity-based)
  │   └─ If triggered: spawn verifier agent
  │
  └─ Process next subtask from queue
```

**Cost Dashboard Shows:**
- Total cost breakdown (LLM vs Worker)
- Cost by role (BOSS: $0.10, MANAGER: $0.25, WORKER: $1.50)
- Cost by model (gpt-4o: $0.80, claude-sonnet: $1.05)
- Real-time updates via Server-Sent Events

### 4. Theoretical Insights

| Topic | Before (Implicit Framing) | After (More Explicit Theoretical Framing) |
|------|---------------------------|-------------------------------------------|
| **Budget as a control variable** | “Budget” is mostly a guardrail to stop tree explosion. | Budget becomes part of the agent **state** $\mathcal{S}$ and a constraint shaping the policy: allocate/spawn/verify/terminate decisions should be budget-aware, not just budget-limited. |
| **Best-of-N subordinates** | Multi-model spawning is “more coverage” but also redundant. | Interpretable as **stochastic search / portfolio selection** under resource constraints: you pay exploration cost up-front and harvest the first-success return, motivating a formal exploration–exploitation tradeoff. |
| **Verification as an action** | Verification is a heuristic bolt-on (random %, complexity-based, “suspicious report”). | Verification becomes an explicit **action** $\mathcal{a}\in\mathcal{A}(\mathcal{s})$ with measurable cost and value; it is best modeled as “pay cost to reduce uncertainty / prevent catastrophic breakdown.” |
| **Catastrophic breakdown failure mode** | Root task decomposition errors propagate and waste work; handled ad-hoc. | This is a structural risk in recursive delegation: early errors create a biased subtree. Theory implication: add **objective-fulfillment checks** (feature $f_2$) and “redo/verify” actions as first-class control levers. |
| **Task queue semantics** | FIFO queue is a pragmatic implementation detail. | Queue length and completion status are **signals/features** (e.g., $f_3$, $f_5$) that shape the supervisor policy: avoid bloat, prefer actions that reduce unfinished work while preserving alignment with the objective. |
| **Reward shaping + boundedness** | Reward/penalty ratios are chosen for engineering convenience. | Reward is a designed learning signal: combine correctness/alignment, verification outcomes, budget efficiency, and delay penalties; keep components bounded to stabilize learning updates (especially under approximation). |
